# Fetching sequencing data and metadata with nf-core/fetchngs

## Overview

[`nf-core/fetchngs`](https://nf-co.re/fetchngs/) is an nf-core Nextflow pipeline for downloading sequencing data and associated metadata from public repositories.

It can be used to retrieve:

* Sequencing reads, typically as compressed FASTQ files (`*.fastq.gz`)
* Sample and run metadata
* An nf-core-compatible samplesheet
* Accession information required for downstream analyses

This document describes a basic workflow for fetching **samples and metadata from IDS** using accession IDs as input to `nf-core/fetchngs`.

---

## 1. Requirements

The workflow requires:

* [Nextflow](https://www.nextflow.io/)
* Access to an execution environment supported by nf-core, such as:

  * Apptainer/Singularity
  * Docker
  * Conda
* Internet access from the machine or HPC node performing the download

Check that Nextflow is available:

```bash
nextflow -version
```

For HPC environments, Nextflow and Apptainer/Singularity may already be available as modules.

For example:

```bash
module load nextflow
module load singularity
```

The exact module names depend on the HPC system.

---

## 2. Get nf-core/fetchngs

Nextflow can automatically retrieve the pipeline when it is first executed:

```bash
nextflow run nf-core/fetchngs --help
```

Alternatively, pull the pipeline explicitly:

```bash
nextflow pull nf-core/fetchngs
```

To see the available parameters:

```bash
nextflow run nf-core/fetchngs --help
```

It is recommended to use a specific pipeline release for reproducibility:

```bash
nextflow run nf-core/fetchngs \
    -r <VERSION> \
    --help
```

Replace `<VERSION>` with the required `nf-core/fetchngs` release.

---

## 3. Prepare the IDS accession list

Create a text file containing the accession IDs for the samples that need to be downloaded.

For example:

```text
SRR12345678
SRR12345679
SRR12345680
```

Save the file as:

```text
ids.txt
```

The accession type depends on how the sequencing data have been deposited in the public repository.

Accessions may correspond to studies, experiments, samples, or sequencing runs. `nf-core/fetchngs` resolves supported accessions to the corresponding sequencing records.

---

## 4. Download samples and metadata

Run `nf-core/fetchngs` using the IDS accession file:

```bash
nextflow run nf-core/fetchngs \
    --input ids.txt \
    --outdir results \
    -profile singularity
```

This instructs the pipeline to:

1. Read the accession IDs from `ids.txt`.
2. Resolve the corresponding sequencing records.
3. Retrieve the available metadata.
4. Download the sequencing reads.
5. Generate files suitable for downstream nf-core workflows.

---

## 5. Output

After the workflow completes, inspect the output directory:

```bash
ls results/
```

The precise directory structure can vary between `nf-core/fetchngs` releases, but the results generally contain the downloaded sequencing data and metadata generated by the pipeline.

### FASTQ files

Sequencing reads are downloaded as FASTQ files.

For paired-end sequencing, files will typically resemble:

```text
SAMPLE_1.fastq.gz
SAMPLE_2.fastq.gz
```

where:

* `_1.fastq.gz` contains read 1
* `_2.fastq.gz` contains read 2

For single-end sequencing, there will normally be one FASTQ file per sample/run.

### Metadata

`nf-core/fetchngs` also retrieves metadata associated with the supplied accessions.

Depending on the repository and pipeline version, this can include information such as:

* Sample accession
* Run accession
* Experiment accession
* Study/project accession
* Library information
* Sequencing platform
* Layout (`SINGLE` or `PAIRED`)
* Sample attributes available from the source repository

The generated metadata should be retained alongside the FASTQ files because it provides the link between the downloaded sequencing data and the original IDS/public repository records.

### Samplesheet

One particularly useful output is the generated samplesheet.

This can often be used directly, or with minor modifications, as input for downstream nf-core pipelines.

For example, an RNA-seq workflow may subsequently use:

```bash
nextflow run nf-core/rnaseq \
    --input samplesheet.csv \
    --outdir rnaseq_results \
    ...
```

Always check that the generated samplesheet contains the required biological sample names and grouping before starting downstream analyses.

---

## 6. Recommended directory structure

A simple project structure is:

```text
project/
├── ids.txt
├── data/
├── metadata/
└── work/
```

Alternatively, allow `fetchngs` to maintain its standard result structure:

```text
project/
├── ids.txt
├── results/
│   └── ...
└── work/
```

The `work/` directory is generated by Nextflow and contains intermediate workflow files.

Do **not** delete `work/` while a workflow is running.

---

## 7. Running on an HPC system

For large datasets, `nf-core/fetchngs` should preferably be run as an HPC job rather than on a login node.

The exact configuration depends on the HPC scheduler.

A typical command remains:

```bash
nextflow run nf-core/fetchngs \
    --input ids.txt \
    --outdir results \
    -profile singularity
```

If an institutional nf-core/Nextflow configuration is available, use the appropriate institutional profile.

For example:

```bash
nextflow run nf-core/fetchngs \
    --input ids.txt \
    --outdir results \
    -profile <HPC_PROFILE>
```

---

## 8. Resuming an interrupted download

Nextflow caches completed tasks.

If the workflow stops because of a network problem, scheduler interruption, or another temporary failure, rerun the **same command** with `-resume`:

```bash
nextflow run nf-core/fetchngs \
    --input ids.txt \
    --outdir results \
    -profile singularity \
    -resume
```

This allows Nextflow to reuse successfully completed tasks rather than restarting the entire workflow.

The `work/` directory must still be available for `-resume` to work correctly.

---

## 9. Verify the downloaded samples

After downloading the data, check that the expected FASTQ files are present:

```bash
find results -name "*.fastq.gz"
```

Count them with:

```bash
find results -name "*.fastq.gz" | wc -l
```

It is also useful to compare the retrieved run/sample accessions against the original IDS accession list.

Check the FASTQ files before starting downstream analysis:

```bash
gzip -t results/path/to/sample.fastq.gz
```

A successful command with no error indicates that the gzip file is structurally valid.

For multiple FASTQ files:

```bash
find results -name "*.fastq.gz" -print0 |
    xargs -0 -n1 gzip -t
```

---

## 10. Keep metadata with the sequencing data

The metadata downloaded by `nf-core/fetchngs` should be retained with the project.

A useful principle is:

```text
IDS accession
      │
      ▼
nf-core/fetchngs
      │
      ├── FASTQ sequencing data
      │
      ├── repository metadata
      │
      └── nf-core samplesheet
                 │
                 ▼
        downstream analysis
```

This preserves provenance and makes it possible to trace each analysed sample back to its original repository accession.

---

## 11. Reproducibility

Record the `nf-core/fetchngs` version used for each download.

The Nextflow execution report and pipeline information should be retained with the project.

A reproducible command should specify the pipeline version:

```bash
nextflow run nf-core/fetchngs \
    -r <VERSION> \
    --input ids.txt \
    --outdir results \
    -profile singularity
```

Also retain:

```text
ids.txt
```

along with the generated metadata and samplesheet.

Together, these provide a record of:

```text
IDS accessions
      +
fetchngs version
      +
retrieved metadata
      +
FASTQ files
```

and make the dataset easier to reproduce or update later.
